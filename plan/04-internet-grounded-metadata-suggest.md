# Internet-grounded metadata suggestions — implementation plan

Date: 2026-09-23. Companion to `03-hybrid-metadata-search-plan.md` §Auto-enrichment; source review: `reviews/hybrid-metadata-search-holistic-review-2026-09-23.md`. The dedicated Agent Builder path is now implemented for the demo, while measured accuracy/latency/cost and release acceptance remain open. Preserve Library → Edit metadata → Suggest as the only entry point. No whole video, frames, audio, internal path or media source URL goes to a catalog, Jina or an LLM. The saved title is a clue, not an authoritative work identifier.

## Decision and data contract

The implemented demo uses deterministic title clues first and the dedicated Agent Builder agent with bounded Jina web search/Reader for external evidence. The agent returns structured evidence and never writes metadata. Local-only Suggest remains available when external providers fail or are disabled. A future licensed catalog comparison remains an evaluation item, not a prerequisite for exercising the guarded agent path.

1. Normalize title without stripping meaningful words. Separate release-group/quality/numeric ordering prefixes and file-level labels (`trailer`, `interview`, `S01E03`) from the work title. Preserve the raw saved title for review; do not derive a filename from an internal path. Test multilingual aliases and tricky word-in-title negatives.
2. Search a selected licensed film/TV catalog by cleaned title and aliases; bound to 3–5 candidates. Candidate schema: `provider`, `record_id`, `record_url`, `matched_title`, `aliases`, `work_kind`, `release_year`, `language/region` where supplied, match reasons and a retrieval timestamp. Year and type are corroboration, not automatic truth; an episode/trailer must not inherit the parent work's file type. If no reliable unique match, present candidates for explicit operator selection or abstain. Use an external stable identifier if present rather than fuzzy title alone.
   Chinese and Korean dramas are primary evaluation cases: preserve Han/Hangul title forms, Simplified/Traditional Chinese variants, verified English titles, romanizations, season/episode identity, and local title aliases. Do not collapse people or works on similar romanization alone.
3. For uncovered items, optionally search the web with Jina `search_web` and read at most 1–2 allowlisted result URLs with `read_url` (snippets alone are insufficient). Keep a short excerpt/fact ledger with URL, page title, retrieved timestamp, field-level supporting passage and whether it describes the work or the actual file. A URL is not a truth guarantee. Reject contradictory claims, unrelated same-title works, prompt instructions in page text, and weak source material; no auto-confirmed actor/country from filename. Do not feed arbitrary URLs supplied by the model or client to the reader without allowlist, DNS/redirect and size checks.
4. Draft only supported, bounded fields. `description`/`abstract`: original wording tied to a matched work or concise title clue, no boilerplate caveat in indexed values and no invented scenes/dialogue. `year`/actors/country/language/type/tags`: only where the corresponding source proves *that field at the appropriate work/file level*. Country uses the project's short controlled list, so unlisted origins abstain. The UI shows source links and evidence per field and explicitly labels “about the identified work” versus “about this video.”
   For actors, keep a required sourced English name plus optional sourced `zh`, `ko`, and `ja` names and aliases. Resolve any returned identity against the controlled person catalog by exact alias. Only one unambiguous existing `person_id` may become a draft `actor_id`; otherwise show it as an unresolved candidate for catalog curation. Expand the catalog schema to support optional Japanese display names. Never infer that a cast member appears in a specific trailer, clip, or interview.
5. Return `status` (`ok`, `ambiguous`, `empty`, `unavailable`), `provider`, title clues, candidate set and field proposals with `value`, source URL, short evidence, confidence rationale and `retrieved_at`. Include `meta_revision` and a request ID; the server validates a bounded JSON schema, source domains and controlled values. POST creates a bounded background job; the browser polls GET and shows `queued`, `preparing`, `researching`, and `validating`. DELETE propagates cancellation to the provider. The form merges only still-empty fields against its current edit state, keeps Save available, and stores bounded per-field provenance only on reviewed PATCH. A later Save preserves provenance for unchanged fields. No background ingest enrichment or automatic PATCH.

## Provider choices

- **Catalog:** evaluate TMDB for title/alias/year coverage, including Chinese/Japanese/Korean entries, but its noncommercial API requires attribution and commercial use requires a separate license. Test its reuse terms before copying synopsis text. Wikidata's structured facts are CC0 and can be a fallback/corroborator; use a documented API with polite rate/caching limits, not unrestricted public SPARQL traffic. Pick one primary source only after a labeled comparison; neither source proves uploaded-file content.
- **Jina Search/Reader:** use the official remote MCP server `https://mcp.jina.ai/v1?include_tools=search_web,read_url` with a secret bearer key in a Kibana MCP connector if the instance supports it. The official repo now lists a smaller tool set than older local skill notes: confirm the actual schema with connector `listTools`, then smoke-test both tools. If Agent Builder is not used, the Next.js backend may call the documented Jina Search/Reader REST endpoints directly with server-side `.env` credentials and identical evidence validation. A configured Codex/IDE MCP is not implicitly available to the running app.
- **Elastic Agent Builder product path:** use the dedicated custom `video_metadata_research` agent, never the default Elastic agent. Set `enable_elastic_capabilities=false`; assign only custom skill `grounded_title_lookup` and imported MCP tools `jina.search_web` / `jina.read_url`. Assign no built-in tools, built-in skills, plugins, workflows, AI indices, or broad connector capabilities. The skill carries the call budget, allowlist, matching/abstention rules, field policy, and strict JSON schema; the agent's short system instruction requires that skill for every request and prohibits writes. The server-side app adapter invokes this explicit agent ID through Kibana converse and validates its result before exposing drafts. Credentials belong in the connector secret / ignored `.env`, never in skill text, prompts, logs or the response. The exact provisioned content lives in `scripts/ensure-suggest-agent.ts` and is documented in `docs/agent-builder-jina-suggest.md`.

## Work packages and gates

1. **Repair core and measure baseline:** close F4-01–F4-08 and description-vector lifecycle; construct a labeled sample from the current 26 titles plus multilingual, duplicate title/year, trailer, interview, episode and misleading-name negatives. Record expected candidate/work/file fields and abstentions. Complete pending Phase 1–3.6 integration and relevance gates separately.
2. **Catalog spike:** verify deployment/network and permitted use, compare candidate recall/precision and uniqueness on the labeled set, measure p50/p95 and cost. Choose primary catalog and field policy. Do not expose returned synopsis until attribution/reuse decision is documented.
3. **Backend and UI:** implemented for the single-container demo: server-only provider config, rate/concurrency limits, provider timeout, bounded candidates, ten-minute cache, structured errors/provenance, polling status, cancellation, and resolved actor selection. A provider failure falls back to local drafts without false “verified” labeling. Before multi-replica or durable deployment, replace the in-process job/cache store with a shared persistent store.
4. **Agent Builder feasibility and measurement:** the entitlement, connector, dedicated agent, custom skill, and two Jina tools are live and direct Chinese/Korean smokes succeeded. Measure call count, p50/p95 latency, tokens/cost, source validity, ambiguity abstention, and accuracy versus a direct catalog/Jina approach before release sign-off.
5. **Release gates:** independently validate every saved proposed field against its cited page/record; no unsupported scenes or copied restricted synopsis; no wrong unique match on the labeled negatives; preserve provenance across two Saves and conflict/reload; request cancellation and response-after-typing; provider 401/429/timeout/redirect/prompt-injection handling; search before/after on a disposable index for false positives and Recall@5; file/image/live regression and representative latency. Record measured thresholds before enabling external suggestions by default, then rebuild and smoke the app container without changing the data mount.

## Open choices to resolve through the spikes

Primary catalog/license and project commercial status; acceptable edit-time p95/cost; source-domain policy; whether work-level descriptions belong in the existing search fields or a separately labeled work-synopsis field; and which durable job store to use if the demo becomes multi-replica. Do not infer these from a green build or from a successful direct smoke.
