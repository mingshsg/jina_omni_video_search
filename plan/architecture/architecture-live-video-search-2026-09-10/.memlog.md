- (direction) Coaching-path build substrate for implementers; requirements, architecture, implementation, and verification are reconciled before each phase advances.
- (decision) Paradigm: ports-and-adapters around a persistent streaming pipeline; transport adapters feed normalized fragments while control, processing, embedding, storage, and query remain separable.
- (constraint) Inherited: provider identity and variant isolation, dual visual and audio vectors, 1024 dimensions, provider byte budgets, RRF semantics, secret handling, and bilingual EUI UI.
- (decision) AD-1: Next.js is the control plane only; a dedicated Node worker is the sole owner of long-running FFmpeg and window processing.
- (decision) AD-2: All protocols terminate behind LiveSourceAdapter; RTSP over TCP is first, HLS and SRT are later adapters, and WHIP terminates at MediaMTX before worker consumption.
- (decision) AD-3: Capture uses HLS temp-file publication for target-2-second fragments; WindowAssembler groups four finalized fragments and advances three while storing actual PTS coverage.
- (decision) AD-4: Window identity is session_id plus stream_epoch plus sequence_no; source_id remains document provenance. Reconnect or timestamp discontinuity increments stream_epoch and sequence is monotonic within an epoch.
- (decision) AD-5: Elasticsearch live session document is the shared control-state authority; source CAS serializes deterministic session claims, the worker alone advances runtime state/revision, and the MVP uses one OS-locked worker plus one web replica.
- (decision) AD-6: A filesystem spool and append-only manifest own sequence allocation, finalized media, searchable intent, event publication, terminal acknowledgment, explicit drop, and expiry; recovery scans all nonterminal records, including stopped sessions.
- (decision) AD-7: Visual and audio inference execute concurrently under the existing provider gate; a bounded indexing-ack queue records searchable intent and reserves revision before bulk create plus refresh wait_for, then publishes the event before terminal acknowledgment.
- (decision) AD-8: Live sessions use live-video-sessions and live chunks use a time-oriented live-video-chunks data stream with @timestamp and Data Stream Lifecycle retention; recovery searches logical IDs across backing indices before create, retrieval collapses by chunk_id, file indexes remain unchanged, and no local Elasticsearch is installed because every process uses the .env endpoint.
- (decision) AD-9: Live search requires variant and explicit session IDs in follow mode, reuses the current retrieval core with live filters, and caches unchanged query vectors while retrieval reruns on searchable events.
- (decision) AD-10: Search results play retained per-window clips; live-view playback is served by MediaMTX HLS or WebRTC and is not coupled to semantic indexing.
- (decision) AD-11: The API stores a validated secret-reference name in pending_validation; only the worker resolves structured connection secrets, validates every address, records safe provenance, and uses argument arrays, an adapter whitelist, and egress binding.
- (decision) AD-12: Backpressure is explicit: bounded work and indexing-ack queues, separate spool quotas, reserved manifest headroom, atomic drop_oldest, and failure when no safe drop is possible.
- (decision) AD-13: Acceptance persists monotonic stage durations and UTC anchors for fragment/window close, inference, indexing, and searchable acknowledgment, plus queue depth and reconnect counters.
- (decision) AD-14: Each session snapshots validated source revision and endpoint fingerprint; reconnect must match that fingerprint or fail and require a new session.
- (decision) AD-15: Durable typed events use per-session revisions and an outbox sequence so every visible chunk can recover its searchable event.
- (decision) AD-16: RTSP time uses a measured receive anchor with explicit uncertainty; no packet-level precision is claimed until the capture mechanism proves it.
- (decision) AD-17: Session creation always requests running; allowed state transitions and reason codes are fixed, and disabling a source does not implicitly stop its active session.
- (decision) Brownfield search cannot satisfy follow-vector reuse with query_vector_builder; live EIS search calls inference once per cache miss and supplies query_vector to every branch.
- (decision) Web and worker use separate environment surfaces; web rejects LIVE_SOURCE_* secrets, and the MediaMTX fixture publisher runs in a separate FFmpeg-capable service.
- (version) Existing seed: Node.js 22, Next.js 14.2.35, React 18.3.1, EUI 119.1.0, FFmpeg 8.1.1, Elasticsearch Serverless observed 9.6.0, Jina omni small 1024 dimensions.
- (version) Gateway/test seed verified 2026-09-10: MediaMTX 1.21.0; WHIP is IETF RFC 9725; FFmpeg documents RTSP TCP and SRT support.
- (assumption) One active source is the first capacity target; live window-processing concurrency defaults to two, with visual and audio calls for each window parallelized under the provider gate.
- (assumption) The initial live source is RTSP over TCP; MediaMTX is mandatory for deterministic E2E fixtures and browser WHIP but optional for direct production RTSP pull.
- (question) Retention defaults and simultaneous-stream target require user confirmation before production hardening.
- (question) Whether WHIP browser publishing is release-one scope requires user confirmation; architecture keeps the adapter boundary ready.
- (event) Architecture inputs reconciled: existing file flow remains separate, and every live capability maps to a boundary and owner.
