topic: Live video indexing and search
updated: 2026-09-10T12:30

- (direction) User requested repository planning documents, implementation plan, tracked TODO, and archival of prior file-video reviews.
- (constraint) The live feature starts from commit 78d7e56 on branch live-video-search; existing file ingest and search remain supported and are not rewritten as live-only behavior.
- (capability) CAP-1: An operator can register, start, stop, and inspect a remote live source; success is an RTSP-over-TCP source reaches live state and reconnects after a controlled interruption.
- (capability) CAP-2: The system emits fragment-aligned windows from four finalized fragments every three fragments, targeting 8-second coverage and 6-second cadence while storing actual PTS boundaries.
- (decision) Recovery queries logical IDs across every data-stream backing index before create and live retrieval collapses by chunk_id because Elasticsearch _id uniqueness is per backing index.
- (decision) Before Phase 3, a disposable 50-window spike validates HLS temp-file finalization, fragment drift, receive-anchor uncertainty, EIS concurrency, and Serverless visibility latency.
- (constraint) Elasticsearch is external only: no local installation or container; all setup, spikes, and runtime calls use ELASTICSEARCH_URL and ELASTICSEARCH_API_KEY from .env.
- (capability) CAP-3: Each completed live window is embedded and becomes searchable without waiting for the stream to end; success is a searchability event only after Elasticsearch can retrieve the document.
- (capability) CAP-4: A user can search live windows by text or image and filter by source, session, time range, and modality; success is new matching windows appearing without re-embedding an unchanged query.
- (capability) CAP-5: An operator can see connection state, capture lag, inference lag, queue depth, drops, reconnects, and per-window failures; success is a fault visible with a stable code and timestamp.
- (capability) CAP-6: A search result can show a thumbnail and play its retained short clip; success is playback aligned to the indexed window timestamps.
- (capability) CAP-7: The worker can restart and recover finalized unindexed windows from a persistent spool; success is idempotent recovery without duplicate documents.
- (capability) CAP-8: Remote-source access is constrained and secrets are not persisted or returned; success is blocked private or unapproved destinations and redacted source provenance.
- (constraint) Retain the existing pluggable providers, provider isolation, 1024-dimensional vectors, dual visual and audio tracks, byte-budget encoder, and RRF search semantics.
- (constraint) Long-running capture and inference cannot live inside a Next.js request lifecycle; a dedicated worker owns source processes and window processing.
- (constraint) User requests contain only an allowlisted credential-reference name; only the worker resolves its structured environment secret, whose base URL contains no userinfo.
- (constraint) The first build slice supports RTSP over TCP; HLS and SRT are adapter extensions; browser contribution through WHIP terminates at a media gateway rather than the Next.js app.
- (constraint) Live chunk records use separate storage from file chunks because lifecycle, timestamps, retention, and session identity differ.
- (assumption) Default live window is 8 seconds with 2 seconds overlap, derived from the measured fine-window throughput and subject to a latency and relevance benchmark.
- (assumption) MediaMTX 1.21.0 is the integration-test and optional protocol-gateway seed; direct FFmpeg pull remains valid for RTSP MVP.
- (assumption) Default searchable metadata retention is 7 days and local clip retention is 24 hours until the user selects policy.
- (assumption) Initial deployment supports one active stream on one developer machine; concurrency is measured before raising the limit.
- (question) What retention periods are required for vectors, thumbnails, and playable clips?
- (question) How many simultaneous live streams must the first production-like deployment sustain?
- (question) Is browser-camera publishing through WHIP required in the first release or after remote RTSP acceptance?
- (note) Non-goals: sub-second semantic availability, a general broadcast CDN, multi-tenant authentication, face recognition, alerts, and replacement of file-video search.
- (decision) Success signal: a deterministic live fixture streams for 10 minutes, survives one disconnect, indexes searchable windows with initial p95 close-to-searchable lag at or below 10 seconds, drops no windows at one-stream target load, and returns aligned playable results.
- (event) Spec coherence pass completed: every capability has intent and testable success; assumptions and open questions are explicit.
- (event) Spec preservation pass completed: live-feed request and inherited file-search constraints are represented; presentation-only conversation content was omitted.
- (decision) Comprehensive review selected: source secrets are worker-only; session creation uses deterministic source claims; all durable worker events use a manifest-backed outbox; RTSP readiness precedes optional protocols.
- (decision) Follow mode requires explicit sessions and a variant, performs full filtered top-K retrieval on searchable events, and uses one web replica until shared handles are designed.
- (event) Planning review completed with no implementation claim; runtime, target Elasticsearch, protocol, resilience, latency, security, playback, and regression gates remain open.
