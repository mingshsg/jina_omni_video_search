# 混合元数据检索（规划摘要）

详细英文方案见
[`plan/03-hybrid-metadata-search-plan.md`](../plan/03-hybrid-metadata-search-plan.md)。

## 要解决什么

在现有「按画面/音频找瞬间」之上，为每部视频增加**可选**元数据（简介、年份、演员、类型、主语言、制片国家等），支持对**已索引视频**补录/编辑，并用于**混合检索**。

## 已锁定决策（2026-09-22）

| 项 | 决策 |
| --- | --- |
| 国家/地区 | 存 **ISO-3166-1 alpha-2** 代码；仅提供下方 20 个常用选项，UI 显示 `代码 — 名称` |
| 自动建议 | 仅在片库 **编辑元数据** 时提供「建议」按钮，导入阶段不做 |
| 结果形态 | **只要瞬间卡片**；整片信息（含人名）通过混合排序提高命中，不另开「整片结果」页 |

**国家/地区下拉（20 项）：** 欧盟选项 `DE` 德国、`FR` 法国、`IT` 意大利、`ES` 西班牙、`NL` 荷兰、`PL` 波兰、`SE` 瑞典、`IE` 爱尔兰；东亚 `CN` 中国、`HK` 香港、`TW` 台湾、`KR` 韩国、`JP` 日本；东盟选项 `SG` 新加坡、`MY` 马来西亚、`ID` 印度尼西亚、`TH` 泰国、`VN` 越南、`PH` 菲律宾；另保留原示例 `US` 美国。编辑、过滤和 API 验证共用此清单，只存代码。字段含义是主要制作国家/地区，而非故事地点或拍摄地点。

## 推荐做法

1. **结构化字段 → 硬过滤**（年份、类型、语言、国家、演员、标签）。用**单次请求**取得全部符合条件的资产 ID（`size: 10000`、`track_total_hits: 10001`），不在交互路径上做分页循环；超过规模上限返回 `FILTER_SCOPE_TOO_LARGE`，不能悄悄截断。没有选任何 facet 时直接省略 ID 过滤，只保留 `variant_id`。  
2. **双路找候选片段**：一路在全部符合硬过滤的视频中做全局画面/音频 knn；另一路用标题、简介、摘要、演员名的 BM25 选出 `A = min(20, max(5, ceil(0.2 × 符合条件资产数)))` 部视频（并设最低分门槛），再在其中各取少量最相关的片段。本仓库演示库约 36 部视频，固定取前 20 会覆盖约 56% 的库，等于让「进入前 20」失去区分度，因此窗口随库大小伸缩。合并并去重后排序。因此人名匹配的视频即使没进入全局 knn 前列，仍有机会出现；没有元数据的视觉命中也保留。  
3. **应用层融合排序**：每个片段有画面/音频名次，另外继承所属视频的一次 BM25 名次；按方案中的明确公式计算。**文本权重初值为 0.4，而不是 1**：在 rank constant 60 下，文本项区间（`1/61`…`1/80`）整体不低于单一模态项区间（`1/61`…`1/260`）的上限，若取 1，仅仅「进入文本候选窗口」就约等于「全库最佳画面命中」。跨索引的资产→片段关系由应用处理，并非 Elasticsearch 自动 join/RRF。数值窗口、权重和多样性限制都是待测的初值。  
4. 查询文本**只做一次嵌入**并在各路复用；现有 EIS 文件检索走 `query_vector_builder`（推理在 ES 内部，应用拿不到向量），混合路径改用应用侧 `embedTextQueryVector`。在比较「开/关混合」的效果之前，必须先验证两条推理路径结果一致（余弦 ≈ 1.0），否则对比不成立。  
5. 元数据只写 `video-assets`，**不必重跑片段 embedding**。导入任务后续更新只修改任务字段（局部更新，数组整体替换），不能整份覆盖已编辑的元数据；编辑冲突返回 409。冲突判定放在脚本内部按 `meta.revision` 比较，而不是文档级 `if_seq_no`，否则导入进度写入会误伤正在进行的编辑。  

**延迟预算（初值，待实测）：** 混合检索是四个串行阶段，不是「两次 ES 往返」。资产枚举 + BM25 300ms、查询嵌入 400ms、各模态 knn 700ms、应用层融合与分组 100ms，端到端 p95 目标 **1,500ms**；各阶段耗时随响应返回，超出即为调优信号。

## 演员姓名与多语言（第三轮新增）

韩国演员同时有 `이정재` / `李政宰` / `Lee Jung-jae` 等写法，用户可能用其中任意一种检索。**姓名不是字符串，而是带别名集合的实体**：用 **`config/people.json`** 人物目录作为事实来源（**不放 `data/`**——那里被 `.gitignore`/`.dockerignore` 排除，且 Compose 会用媒体卷盖掉，放进去既不会提交也不会进镜像），编辑器只存**人物 ID**，服务端把别名展开写入资产。

**写入/查询契约（只说一次）：** 客户端 PATCH **只传 `actor_ids`**，服务端校验目录（未知 ID → `400 META_UNKNOWN_ACTOR_ID`）后派生 `actors`（展示名）、`actor_aliases`、`actor_keys`、`search_text`。MVP 的 API **不接受自由文本人名**——人名不是稳定身份、可能对应多个人，消歧属于自动补全 UI 里由人来做，不该塞进服务端启发式。搜索侧的演员 facet 是 `filters.actor_ids`，ANY 语义。

- `actor_ids`：唯一的演员过滤字段，无论元数据用哪种文字录入都能命中；原 `actors_key` 作废。
- `actor_aliases`：全部别名，`copy_to` 进 `meta.search_text`，供 BM25 召回。
- `actor_keys`：每个别名再派生「去分隔符」（`leejungjae`）和「词序排序」（`jae|jung|lee`）两个键，吸收拼写与姓名顺序差异。两者不叠加，**别名表才是主力，键只是廉价兜底**。

**分词器：** 现有索引没有配置任何 analyzer，默认 `standard` 会把 `李政宰` 拆成单字 `[李, 政, 宰]`，任何含「李」的视频都会命中，属于精度崩塌。至少为 `meta.search_text` 增加 `cjk` 子字段（二元组）；Phase 1 需先探测目标集群是否自带 `nori`/`smartcn`/`icu`/`phonetic` 插件（`phonetic` 可自动归并 Lee/Yi、Jung/Jeong），**分词器一旦定下无法在不重建索引的情况下更改**。

## 简介是否做向量（Phase 3.5，开关控制）

做。BM25 有两个硬伤：同义改写（查「heist」但简介写「robbery」）和跨语言（中文查询 + 英文简介）。嵌入模型本身跨语言（93 种语言，实测含 en-ko / en-zh / ja-ko），可同时解决两者。

代价极低：入库时每部视频保存元数据时多一次推理（约 36 部）；**查询时零额外推理**，因为查询向量本来就已在应用侧算好，只是多一路 kNN。

两个必须写死的约束：一是 `description_embedding` **绝不能**放进片段向量字段或索引——模型是跨模态共享向量空间，简介向量与画面窗口向量直接可比，同字段会让「简介」被当成「瞬间」返回；二是原则应表述为**片段永不因元数据编辑而重新嵌入**，简介向量是资产级的新增推理，需记录 provider/model/task/dims 并在 provider 变更时失效。

## 单输入框 → 真正的多字段查询（Phase 3.5 / 3.6）

**先说缺陷：** 查询只输入 `이정재` 时，现方案会把「人名」拿去和画面向量比对，候选窗口是噪声；BM25 虽能把正确视频顶上来，但**视频内部的时间点是随机的**，界面却会显示一个看起来很精确的时间戳。这是 H07「不得用元数据证明人物出现在该时刻」换了个入口重现。

**目标契约：** 把单个输入解析成真正的多字段查询，除向量检索外**所有字段都可选**：`vector_query`（残余场景描述，始终参与）、`free_text`（BM25）、`extracted`（演员/年份/国家/类型…）。

**规则 0（不变量）—— 解析器只塑造查询的「输入」；它看不到结果、不直接给分、不写任何用户会读到的文字。**

上一版写成「绝不参与检索与排序」是错的、而且自相矛盾：解析器的全部意义就是决定嵌入什么、并提出 facet 加权，这两件事本来就会改变检索输入和排序。准确的不变量要窄得多：

| 允许 | 禁止 |
| --- | --- |
| 读取用户输入的字符串 | 读取任何向量、片段、资产或检索结果 |
| 输出 `vector_query` / `free_text` / `extracted` | 直接赋值、调整或后处理任何分数与名次 |
| 提出经校验的 facet 加权，交由**确定性**公式生效 | 检索之后重排、过滤或丢弃命中 |
| 被整体跳过而不影响正确性 | 生成、改写、摘要或解释任何展示给用户的文案 |

也就是说：解析器的产物是一个固定、可审计公式的**输入**，而不是作用在结果上的算子。加权公式：`score_hybrid += w_facet × Σ matched(f) / n_selected`，`w_facet` 初值 **0.2**，**低于** `w_text`（0.4），因为推断出来的 facet 证据强度低于用户能看见的词法匹配。手选 facet 是硬过滤、不再加权；同一 facet 既被抽取又被手选时以硬过滤为准，不重复计分。

另外三条规则：

1. **解析出来的 facet 只做加权（boost），不做硬过滤**；用户在面板上亲手选的才是硬过滤。解析结果以可删除的 chip 呈现，点击 chip 才升级为硬过滤。这样解析错误只是排序噪声，而不是「零结果」页面。
2. **输出空间封闭，校验可以做到完备**：所有抽取值都要对照固定词表（20 个国家、10 种类型、语言表、人物目录）校验，认不出来的一律丢弃，模型无法凭空造出国家码或演员。
3. **三级降级**：LLM → 词典匹配 → 原始查询全路广播。未配置解析器时演示必须照常可用。

**词典能做的**（Phase 3.5，永久兜底）：演员别名最长匹配、国家/国民称谓表（约 60 条）、类型同义词表（约 60 条）、年份正则（`1990s`、`60年代`、`before 1970`，约 10 条）。实体空间本身封闭且很小，多数查询无需模型。

**LLM 买的只是「消歧 + 泛化」**（Phase 3.6）：词典无法判断 `Paris` 是城市、演员还是场景，无法判断「Audrey Hepburn interview」里的 interview 是类型还是场景，也无法覆盖未登记的口语说法（表里有「韩国电影」，没有「南朝鲜的片子」）。

**调用方式（2026-09-22 决定）：** 走 **Elastic Inference Service**，直接调用推理 API 的 **`completion`** 任务类型，模型固定为 **`google-gemini-3.5-flash-lite`**（EIS 目录内，GA）。

注意有三个东西都叫 completion，别混：

| 名称 | 是什么 | 本方案是否使用 |
| --- | --- | --- |
| ES\|QL `COMPLETION` 命令 | 一条 ES\|QL 语句命令 | **否** |
| 推理 API `completion` 任务 | `POST /_inference/completion/<id>`，普通请求/响应 | **是** |
| 推理 API `chat_completion` 任务 | `POST /_inference/chat_completion/<id>`，**返回流** | **否** |

```ts
const res = await client.inference.completion({
  inference_id: cfg.QUERY_PARSER_INFERENCE_ID,
  input: prompt,        // 一个字符串：schema + 词表 + 用户查询
  timeout: '800ms',     // 一等公民的超时参数
  task_settings: { },   // 厂商透传，结构化输出设置放这里
});
const raw = res.completion[0].result;   // JSON 字符串 → 解析 → 校验
```

`chat_completion` 的返回类型是流（`StreamResult`），为一次短抽取去处理 SSE 不划算，故不用。现有 `lib/embed/eis.ts` 已经在用同样的 `client.transport.request` 形态，因此：

- **不引入任何新凭证**，复用 `ELASTICSEARCH_URL` / `ELASTICSEARCH_API_KEY`；
- **唯一的应用侧开关是推理端点 ID**，换模型只需服务端 `PUT _inference`，无需改配置、无需重新部署；
- 配置窗口收敛为：`QUERY_PARSER_PROVIDER`（`none|dictionary|eis`）、`QUERY_PARSER_INFERENCE_ID`、`_TIMEOUT_MS`(800，必须显式设置，Serverless 推理默认 120 秒)、`_MAX_TOKENS`(256)、`_FACET_MODE`(boost)、`_CACHE_TTL_MS`、`_CACHE_MAX`。

**不用 Agent Builder**：多轮 + 工具调用，延迟以秒计。**也不用 ES|QL `COMPLETION` 命令**——它其实走的是同一个 `completion` 任务类型，所以这是传输方式之选、不是能力之选。直接调推理 API 的四个理由：① **ES|QL 的 `WITH { }` 只接受 `inference_id` 和 `timeout`，拿不到 `task_settings`**，而结构化输出设置（如 Gemini `responseSchema`）只能从那里传——这是最硬的理由；② 不必把用户查询拼进 ES|QL 语句；③ 不依赖 `esql.command.completion.enabled` 集群开关及其 100 行默认上限；④ 单行查询没有查询规划开销，错误面也更简单。`COMPLETION` 在本功能中**不作他用**，理由见规则 0。

**提示词不是保证。** 精心设计的 prompt 只能让 JSON「大概率」正确；**规则 2 的词表校验才是正确性保障**。Phase 3.6 需先验证 EIS 是否透传 Gemini 的 `responseSchema` / JSON 模式，若不透传则采用「提示词 + 校验 + 一次修复重试」。

**延迟：** 解析是串行环节（要先有残余才能嵌入），不做处理会吃掉 1,500ms 预算。三项缓解缺一不可：解析结果缓存（复用 `lib/live/query-cache.ts` 的形态）、无歧义时直接跳过模型、以及「全量查询嵌入」与「解析」并行投机执行——两者现在都打到同一个服务，实现成本很低。

本仓库既有实测：EIS 文本嵌入约 **157ms**；生成约 150 token 的补全会明显更慢，先按 **400–900ms** 预估并实测校正。另外两点约束：EIS 目录中 Gemini 系列**仅美国区域**，非美区项目要多一跳，且查询文本会离境；解析调用**不得**共用 `EMBED_CONCURRENCY` 并发闸门，否则交互式解析会排在入库嵌入后面。

**名字单独查询时（按阶段拆分）：** `scene_terms_present` 只有「能识别人名的东西」才算得出来，而词典匹配器要到 Phase 3.5 才有——上一版却要求 Phase 3 就给出这个标志，而 Phase 3 的默认路径根本不解析，等于要求一个算不出来的值。

- **Phase 3（无解析器）**：靠**标签契约**——每条命中都把向量证据与「视频元数据匹配」分开标示，任何卡片都不声称人物/事件出现在所示时间点。不需要检测器。顺带一提，降低向量权重本来也不能把「人名推出来的时间戳」变成证据，真正起作用的只有标签。
- **Phase 3.5（有匹配器）**：开启解析且抽不出场景词时，向量通道照常执行（它是唯一不可选通道），但 `scene_terms_present=false` 额外降低其排序权重，卡片标注「匹配到视频元数据」。

**检索时可开关：** 解析是**搜索时的用户选项**，不只是部署配置——请求里加 `hybrid.parse_query`，UI 上是搜索框旁的「智能解析查询」开关（未配置解析器时隐藏）。

| `parse_query` | 服务端配置 | 行为 | 响应 `parser` |
| --- | --- | --- | --- |
| 省略 | 任意 | **不解析（默认）** | `disabled` |
| `true` | 已配置 | 解析 | `eis` / `dictionary` |
| `true` | `none` | 不解析，且不报错 | `unavailable` |
| `false` | 任意 | **跳过全部解析**（词典 + 模型） | `disabled` |

**默认全关。** 默认检索路径就是**纯 embedding 向量检索**，与今天的行为逐字节一致：省略 `hybrid` 即 `use_text=false` 且 `parse_query=false`，没有 BM25 通道、没有整片排名投影、不解析、不出 chip。混合排序和查询解析都是显式开启。这样对现有演示的回归风险基本为零。

**部分解析、甚至解析后结果没变化，都是合法结果，不是失败。** 解析器不必填满所有字段；纯场景查询本来就没东西可抽，`vector_query` 就是整句输入，结果与不解析完全相同——这是构造上的必然，不记为错误，也不该靠「抽得更狠」去「修」。过度抽取才是真正伤相关性的失效模式。

**简介向量的时效安全：** 推理比保存慢，两次快速编辑可能乱序完成，旧向量会盖掉新描述——provider 失效机制管不到这种情况（provider 根本没变）。因此向量要绑定 `source_revision` + `source_digest` + `state`（`current|stale|failed`）：保存时先标 `stale`，写入前**必须确认 `meta.revision` 仍等于 `source_revision`** 才发布，推理失败则保存照样成功但该字段不参与检索——**语义通道只查 `state: current`**。

**必须能 inspect。** 正因为解析可能在结果上看不出来，就必须有地方看它到底做了什么：响应 meta 带一个 `parse` 对象，UI 在结果旁给一个可折叠的「解析详情」面板，内容包括 `parser`、`vector_query`、`free_text`、**`applied`（已采纳）**、**`rejected`（被词表校验丢弃的值 + 原因）**、置信度、耗时、缓存命中。`rejected` 和 `applied` 一样重要——它是看规则 2 校验是否在工作的唯一窗口，也是调误触发率的主要依据。即使这次解析没改变任何结果，面板也要能打开。

`false` 跳过的是整层解析而不只是模型：原始查询照 Phase 3 的方式广播到各通道，不显示 chip，不推断任何 facet。**开关绝不能影响用户手动勾选的 facet。** 图片检索不接受该参数。

**评测：** 解析器需要独立的约 50 条 `查询 → 期望结构` 标注集，核心指标是**误触发率**而非准确率——漏掉一个 facet 只是排序略差，多加一个 facet 会直接把结果清空。采用规则 1 后这个不对称基本消失，这正是规则 1 排第一的原因。

**证据边界：** 演员表只能证明该演员属于影片，不能证明他/她出现在返回的时间窗。卡片分别标示「视频元数据匹配」与画面/音频片段证据；片段级人物/事件定位需要后续带时间戳的字幕、转写或识别证据。分别评估“找到正确视频”和“找到正确片段”。验收要求**排名双向成立**：人名/片名查询要把元数据匹配的视频带进前 3；纯场景查询（不含人名片名）时混合前 3 应与纯画面前 3 一致，「仍然可被检索到」不算通过。

## 自动抽取

核心检索先支持人工编辑。编辑页可选的本地建议只取明确的文件名年份、媒体语言标签；不自动填演员或国家。简介/类型等生成式建议需要另外确定 caption/LLM/ASR 服务、预算和质量门槛。建议只进入表单草稿，用户保存后才写入；来源与确认状态按**字段**记录，不能覆盖已确认值或用户正在输入的内容。
